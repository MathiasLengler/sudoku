## 1. Correctness check vs Theory Spine

**Verdict: yes, matches the spine** — with a real test-quality defect.

- Scans rows, then columns (`find_swordfish` chains both axis directions), matching spine's "candidate confined to three rows/columns... look in the opposite direction."
- Line filter: `count == 2 || count == 3` per candidate per row/column — matches spine's stated variants Perfect 3-3-3, 2-2-2, and mixes like 3-2-1 (a per-line count of 1 or ≥4 is correctly excluded).
- Combinatorial core: all `C(potential_lines, 3)` triples of qualifying lines; keeps a triple only if `combined_cols.count() == 3` (union of the three lines' candidate-column sets has exactly 3 members) — this is exactly "covering exactly 3 columns/rows," the spine's core Swordfish precondition.
- Elimination: for each of the 3 covered opposite-axis lines, take that line's candidate positions and subtract the swordfish's own 3 base-axis coordinates (`.without(...)`) — i.e. delete the candidate from the 3 covered lines outside the swordfish's own cells. Matches spine: "candidate removed from all other positions on the three aligned rows/columns."
- No-op guard: if `axis_coordinates_to_delete.is_empty()`, pattern is skipped (mirrors "if only the Swordfish candidate itself, nothing to eliminate" from the file's own logic comment).
- Generic over `Base` (runs for Base2–Base5, not just 9×9) — a valid generalization of "n=3 fish," not a spine deviation.

## 3. Pattern description for the owner (prose only)

For each candidate value, build a transposed index of that candidate's remaining positions per row and per column (same shape as X-Wing's private index). Separately for the row-scan and the column-scan direction: keep only lines where the candidate currently occurs in exactly 2 or 3 cells, then examine every combination of 3 such lines; if the union of their candidate-bearing coordinates on the opposite axis has size exactly 3, a Swordfish is found (3 base lines × 3 covering lines, whether or not all 9 intersections actually hold the candidate). Having identified the 3 covering lines, remove the candidate from every cell on those 3 lines that is not one of the Swordfish's own base-line cells; skip patterns that would produce zero eliminations. Repeat for every candidate value and for both directions (rows-as-base and columns-as-base), collecting all resulting deductions.

Required pre-existing data: `Grid<Base>`/`Position`/`Coordinate`/`Candidates`/`CandidatesGroup` (grid module), `Value<Base>::all()`, `Deduction`/`Deductions`/`Action`/`Reason` deduction model, `Deduction::try_from_iters`.

Gotchas/defects:
- Pure O(lines choose 3) triple-nesting per candidate per axis — fine at 9×9/16×16 scale, but a naive rescan (`with_grid` rebuilds the full index from scratch on every `execute()` call, same as X-Wing/GroupIntersection) rather than reusing a persistent index.
- The private `GroupCandidateIndexes` struct plus its `with_grid`/`axis` methods and the `Axis` enum plus `coordinates_to_pos` are **byte-for-byte identical** to the ones already living in `x_wing.rs:221-259` (verified via direct diff of both files) — not just similar, an exact copy-paste with no modification.
- Score (350) and default-solver registration (inserted between XWing and BruteForce, `x_wing:true, swordfish:true` in `default_solver_strategies()`) are ad hoc guesses — the spine's grading page has no published point value for Swordfish (marked `UNKNOWN` in the theory spine), consistent with the codebase's existing "ad-hoc first pass" scoring noted in the baseline.
- Zero real-puzzle validation: because tests are 100% synthetic and only assert loose invariants ("no elimination inside base rows," "eliminations confined to covering columns") rather than an exact expected `Deductions` set, a subtly wrong elimination boundary (e.g. off-by-one on which axis is "covered" vs "base") could pass all 4 tests undetected.

## Fish-family cross-comparison (owned)

**Shape comparison of the three "transposed candidate index" structs:**

| Struct | Location | Fields |
|---|---|---|
| `GroupCandidateIndexes` (X-Wing) | `x_wing.rs:221-259` | `rows`, `columns` (both `CandidatesGroup<Base>`) |
| `GroupCandidateIndexes` (Swordfish, this branch) | `swordfish.rs` | `rows`, `columns` — **identical fields, identical `with_grid`/`axis` method bodies** to X-Wing's, down to variable names (`row_index`, `column_index`) |
| `GroupCandidateIndexes` (GroupIntersection) | `group_intersection/mod.rs:127-175` | `rows`, `columns`, `row_major_blocks`, `column_major_blocks` (adds the two block axes; same `with_grid` scan pattern, extended to also record block indexes) |

The three are not just "close" — Swordfish's struct is a verbatim copy of X-Wing's (same struct name in a different module, same private `Axis` enum with the same `.other()`/`coordinates_to_pos` methods). GroupIntersection's version is a strict superset shape (adds block axes) built with the same per-position scan loop. All three rebuild from scratch on every `execute()` call (no persistence) — this is exactly the gap that the sibling branch `add-persistent-group-availability` (see `.tmp/0-branch-survey.md`) already addresses by promoting this into a formal, persistent `GroupCandidateAvailability<Base>` with `rows`/`columns`/`row_major_blocks`/`column_major_blocks`, computed once and reused across strategies (its own diff refactors X-Wing and GroupIntersection onto it).

**What one shared structure needs to serve X-Wing + Swordfish + GroupIntersection (+ Jellyfish later):** exactly what `add-persistent-group-availability` already built — a single `GroupCandidateAvailability<Base>` (or equivalent) exposing all four transposed axes (`rows`, `columns`, `row_major_blocks`, `column_major_blocks`) per candidate, built once per `execute()`/solver-step rather than per-strategy, with an `.axis(Axis) -> &CandidatesGroup<Base>` accessor (rows/columns) that X-Wing, Swordfish and a future Jellyfish can all consume identically; GroupIntersection additionally needs the block axes, which the persistent struct already carries. A shared `Axis` enum (`Row`/`Column`) with `.other()` and `.coordinates_to_pos()` should live alongside it rather than being re-declared per strategy (currently declared separately, identically, in both `x_wing.rs` and this branch's `swordfish.rs`).

**Is Swordfish a natural n=3 generalization of X-Wing's n=2 approach?** Yes, structurally very close but not code-shared: X-Wing (per baseline) finds, per candidate, a line with an exact 2-candidate lock (a "locked pair") and pairs it against another line with the same 2 coordinates. Swordfish generalizes this to n=3 by (a) relaxing "exactly 2" to "2 or 3" per line and (b) replacing "pairs of lines with an identical coordinate set" with "triples of lines whose *union* of coordinates has size 3" — a strictly harder combinatorial condition than X-Wing's simple equality check, needed because Swordfish's variants (2-2-2, 3-3-3, 3-2-1 per the spine) don't require every line to hit the same exact coordinate set, only that the union stays at 3. This union-based triple-combination approach **could serve as one generic `fish(n)` scan**: for general n, filter lines to "2..=n candidates," enumerate all n-combinations of qualifying lines, keep those whose union of opposite-axis coordinates has size exactly n, then eliminate on the covering lines outside the base lines — X-Wing is the n=2 instance (where "combination has union size 2" reduces to the simpler pairwise-equality check X-Wing currently uses, since 2 lines with ≤2 candidates each summing to a union of 2 forces both to be the identical pair), Swordfish is n=3, and Jellyfish (per the spine's Chaining Strategies family table, `X-Wing Family, ..., Swordfish, Jellyfish, ...`) would be n=4 with the same scan shape, just costlier combinatorially (`C(lines,4)` instead of `C(lines,3)`). The spine documents this progression as an explicit generalization chain: the Swordfish entry itself states "All Swordfishes will break down into X-Wings and because we know X-Wings work, so will the Swordfish," i.e. sudokuwiki treats X-Wing → Swordfish → Jellyfish as literally the same pattern parameterized by n, matching what a shared `fish(n)` implementation would encode.

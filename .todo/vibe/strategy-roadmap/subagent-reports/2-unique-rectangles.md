- Algorithmic redundancy: `find_unique_rectangles` runs **two** independent enumeration passes over the same bivalue-cell groups — an `itertools::combinations(2)` pass over all floor rows × all floor columns, and a second pass that, for every pair of same-row/same-column floor cells, re-scans *all* `Coordinate::all()` for the opposing axis. The second pass is a strict (inefficient) subset of what the first pass already covers; it inflates the search to roughly O(n) extra work per floor-cell pair and exists only because the first pass's row/column universe isn't scoped tightly enough — a sign of exploratory/unrefined code rather than a deliberate two-phase algorithm.

### 3. Pattern description for the owner (prose only)

The strategy first scans the whole grid for cells with exactly two candidates and buckets their positions by which candidate pair they hold. For each bucket, it treats those positions' distinct rows and columns as candidate rectangle edges and tries every row-pair × column-pair combination (plus a redundant same-row/same-column sweep) to build 4-corner rectangles, keeping only those spanning exactly two blocks. For each surviving rectangle it classifies corners into "floor" (exactly the base pair) vs "roof" (base pair plus extras) and, depending on the 3-floor/1-roof or 2-floor/2-roof split, dispatches to a Type 1, Type 2, or Type 4 elimination routine, each independently rebuilding a `Deduction` via manual `actions`/`reasons` map inserts. Required pre-existing data: `Position`/`Coordinate` row/column/block accessors, `Candidates` set operations (`intersection`, `without`, `count`, `to_single`), and the `Deduction`/`Action`/`Reason` types. Gotchas: the Type 4 floor-side branch is theoretically unjustified and untested; the dual enumeration passes are wasteful; the Type 2 elimination is unit-scoped too narrowly (misses cross-unit sightlines); no strategy-level test proves Type 2 or Type 4 correctness against a real puzzle.

### 3. Pattern description for the owner (prose only)

The strategy enumerates every unordered pair of candidate values up front (not seeded from actual bivalue cells), and for each pair scans every row to record which columns hold a cell containing both values of the pair as a subset of its candidates. It then intersects those per-row column sets pairwise across all row pairs to find 4-corner rectangles, filters to those spanning exactly two blocks, and for each surviving rectangle tries Type 1 then Type 2 by classifying each corner as exactly-the-pair (floor) or pair-plus-extras (roof) via a single pass over the four corners. Type 2's elimination scope is computed by requiring a target cell to see roof cell 1 and roof cell 2 via any (possibly different) shared unit each, matching the general "sees both" idiom used by other bent-set strategies in the spine. Required pre-existing data: `Position`/`Coordinate` accessors, `Candidates` set ops, `Deduction::try_from_iters`/`Action::delete_candidates`/`Reason::candidates`, and the repo's `assert_deductions`/`strategy_snapshot_tests!` test scaffolding. Gotchas: enumerating all `C(n,2)` candidate-value pairs regardless of whether any bivalue cell actually holds them is less targeted than seeding from real bivalue cells (more wasted iteration for grids with few candidates in play, though still correct); no Type 4/2B/2C/3/5; branch name is misleading (see naming check above) — do not assume this branch touches the real Rectangle Elimination technique.

## Cross-branch: duplicate reconciliation

**Rectangle-finding approach.** Branch A seeds its search from actual bivalue cells (grouped by candidate pair via a `HashMap`), then enumerates row/column combinations among the rows/columns that contain at least one such cell — cheaper in principle when few bivalue cells exist, but implemented with a redundant second enumeration pass that duplicates the first. Branch B instead iterates every possible candidate-value pair up front (ignoring whether any cell actually holds it) and, per pair, scans all rows for cells containing that pair as a subset, then pairs up rows. Neither approach reuses the codebase's existing `GroupCandidateIndexes`/`GroupCandidateAvailability` transposed-candidate infrastructure noted in the baseline (`group_intersection/mod.rs`, `x_wing.rs`, and the `add-persistent-group-availability` branch) — both branches independently re-derive "which cells in this row contain candidate X" from scratch via a full-grid scan, another instance of the duplication pattern already logged for other strategy branches.

**Type coverage.** Branch A: Types 1, 2 (block/row/column-shared roofs, single-axis elimination scope), 4 (roof-based, correct; plus an unjustified floor-based extension, untested). Branch B: Types 1, 2 only (row/column-shared roofs only, but a more theoretically complete "sees both via any unit" elimination scope). Neither implements Type 2B/2C/3/3b/4B/5, and neither implements the true sudokuwiki "Rectangle Elimination" strategy despite Branch B's branch name claiming to.

**Test coverage.** Branch A: 3 ad hoc unit tests, no snapshots, and its one Type 2 test computes but never asserts the expected condition (a no-op check) — Type 4 is completely untested. Branch B: 1 targeted unit test using the repo's canonical `assert_deductions` helper, plus the full `strategy_snapshot_tests!` macro (8 snapshot files across bases 2–4), matching the repo's documented three-tier test convention. Branch B's testing is materially more rigorous and more idiomatic; Branch A's is the weakest of any tested here (survey's "no snapshot tests" note undersells it slightly — the one substantive Type 2 check present is dead code).

**Better reference verdict.** Branch B (`add-rectangle-elimination-strategy`'s `unique_rectangle.rs`) is the better reference for the owner: it uses the repo's existing `Deduction`/`Action`/`Reason` construction helpers idiomatically, has a theoretically sounder and more complete Type 2 elimination scope, and follows the project's standard test template (unit test + snapshot suite) instead of a dead assertion. Branch A's only real advantage is Type 4 coverage, but that code path includes an unverified, likely-unsound floor-side branch with zero test coverage — if the owner wants Type 4, treat Branch A's roof-side half (only) as a reference and discard the floor-side addition; do not port it uncritically. Neither branch is close to mergeable as-is: pick Branch B's skeleton, keep Type 1/2 logic, discard Branch A entirely except as a cross-check for Type 4's roof-only argument, and rename the "add-rectangle-elimination-strategy" branch's naming confusion out of any port (it is not Rectangle Elimination).

**Uniqueness assumption (shared, feeds SAT-fit analysis).** Both implementations rest entirely on sudokuwiki's stated axiom that "published Sudokus have only one solution" — this is asserted, never checked, by either branch. Neither branch (nor the underlying deadly-pattern argument in general) verifies that the puzzle actually has a unique solution before applying UR eliminations; if fed a multi-solution or malformed grid, both strategies would produce logically invalid eliminations that happen to look structurally correct. The repo already has a SAT-based uniqueness/solution-counting capability (`solver/sat::SolverIter`, used today only for generator pruning and full-grid solving, per the codebase baseline) that could in principle validate the uniqueness precondition before a UR (or any uniqueness-family) strategy fires — this is a candidate integration point for a later SAT-fit analysis, not something either branch attempts.

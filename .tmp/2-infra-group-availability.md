## 1. API shape

New module `sudoku-rs/src/solver/strategic/group_candidate_availability.rs`:

- `enum Axis { Row, Column }` with `other(self) -> Self` and `coordinates_to_pos<Base>(self, axis_coordinate, other_axis_coordinate) -> Position<Base>`. Row/Column only — no `Block` variant, no block-index-to-position convenience (block lookups still go through the pre-existing, unrelated `position::BlockSegment::block_position`/`axis_position` machinery).
- `struct GroupCandidateAvailability<Base> { rows, columns, row_major_blocks, column_major_blocks }`, each a `CandidatesGroup<Base>` (bitset-per-group-index). Methods: `axis(&self, Axis) -> &CandidatesGroup<Base>`, `insert(&mut self, pos: Position<Base>)`, `delete(&mut self, pos: Position<Base>)`. This is the per-candidate transposed view, structurally identical to the two pre-existing private `GroupCandidateIndexes` structs on dev (group_intersection had all 4 fields, x_wing had only rows/columns).
- `struct StrategicGroupAvailability<Base> { candidates: Vec<GroupCandidateAvailability<Base>> }` — one entry per candidate value. Methods: `new()`, `from_grid(&Grid<Base>) -> Self` (full grid scan, same algorithm as the old `with_grid()`s), `get`/`get_mut(Value<Base>)`, `iter() -> impl Iterator<Item=(Value<Base>, &GroupCandidateAvailability<Base>)>`, and incremental-update methods `delete_candidate(pos, candidate)`, `delete_all_candidates(pos, candidates)`, `set_value(pos, previous_candidates)` (the last just calls `delete_all_candidates`).
- `Strategy` trait gains a new method `execute_with_availability<Base>(self, grid: &Grid<Base>, group_availability: &StrategicGroupAvailability<Base>) -> Result<Deductions<Base>>` with a default body that ignores the availability and forwards to the existing `execute()`. This is additive, non-breaking for other strategies.
- Solver wiring: `Solver::execute_strategies_iter` (`strategic/mod.rs`) now does `let group_availability = StrategicGroupAvailability::from_grid(self.grid.as_ref());` **once per call**, then calls `execute_with_availability` for every strategy in the iteration instead of `execute`.

**Verdict on the Notion vision**: partially delivered, and the important half is missing. The struct is shared **across strategies within one solver step** (one `try_strategies()`/`try_all_strategies()` call), which is the "passed to each strategy" part of the vision. But it is **not persistent across steps**: `execute_strategies_iter` is a method on `&self` called fresh every time the human-style solve loop restarts after an applied deduction (per baseline doc, the loop restarts from the top after every deduction), so `from_grid()` — a full grid rescan — runs on every single step regardless. The incremental-update API (`insert`/`delete`/`delete_candidate`/`delete_all_candidates`/`set_value`) is fully implemented and unit-tested in isolation, but **grep confirms zero call sites** outside the module's own `#[cfg(test)]` block — it is never invoked from the deduction-application path (`deduction/action.rs`, `Deductions::apply`) or from the solver loop. So the "computed once by the solver, updated on grid changes" half of the Notion task is unbuilt dead code; only the "same instance passed to each strategy" half within a single step is done.

Threading mechanism: new trait method + solver-held local variable recomputed per iterator invocation, not solver-held persistent state (no field added to `Solver`/`SolverBuilder`).

## 3. Gap vs Notion vision

- **Persistence**: not delivered (see #1) — rebuilt every solve step via a full `Position::all()` grid scan.
- **Incremental update**: API surface exists (`insert`/`delete`/`delete_candidate`/`delete_all_candidates`/`set_value`) and is unit-tested standalone, but is never wired to the actual deduction-application path. It is unreachable dead code from the running solver's perspective.
- **Benchmarks**: two `criterion` benchmarks added in `sudoku-rs/benches/sudoku_benchmark.rs`, both just `StrategicGroupAvailability::from_grid(grid)` timed on two sample grids (`sample_grid_hidden_singles`, `sample_grid_pointing_pairs_2`). These measure raw construction cost in isolation; there is **no comparison benchmark** against the old per-strategy-duplicated construction cost, no benchmark of the full solve loop with/without sharing, and no benchmark that would show whether incremental update (were it wired up) would actually beat full-rescan-per-step — i.e., the actual question the Notion task poses ("benchmark whether construction is a bottleneck") is not really answered, just instrumented.
- **Extensibility to other cross-strategy structures**: not addressed at all. No bivalue-cell index, no chain/strong-link scaffolding, no generalized "solver-held state bundle" concept — this PR only touches the one existing duplication (group-candidate transposition), not the broader idea of a general persistent-state-for-strategies mechanism.

## 4. Pattern description (prose)

Conceptually the structure answers, for one candidate value at a time, "in which row/column/block is this candidate still available, and at which position within that group?" by storing one bitset (`CandidatesGroup`, essentially `[Candidates; SIDE_LENGTH]`) per group axis, indexed by group number, where each bit says whether the candidate occupies a given coordinate within that group. It is built by a single full-grid walk that, for every cell with candidates, inserts each remaining candidate into its row-bucket, column-bucket, and two independently-indexed block buckets (row-major and column-major order within the block, so the same block membership can be read either "by row order" or "by column order" depending on which strategy needs it). Queries are then O(1) bit operations: popcount to ask "how many cells in this row still have candidate 5," bit-AND/mask to ask "which of these positions are outside this block segment," or an integer/bitset equality to compare two groups' candidate footprints (the trick XWing uses to detect a matching locked pair in two different rows).

Worth keeping: the group-index dictionary pattern itself — collapsing three independent strategy-local reimplementations of the same idea into one canonical type is straightforward, low-risk, and the diff proves it's behavior-preserving. The dual row-major/column-major block encoding is a real design decision (not incidental) that lets both "block reduces axis" and "axis reduces block" directions of GroupIntersection share one structure without re-deriving indices.

Worth redoing: the incremental-update half was designed and unit-tested but never connected to anything — either finish the wiring (call `delete_candidate`/`set_value` from `Deduction::apply`/`Action::apply`, and hold `StrategicGroupAvailability` as solver state that persists across `SolverPathIter` steps rather than being a local in `execute_strategies_iter`) or drop the API until it's needed, since currently it's unreachable and unverified against a live solve loop (only checked against synthetic single-insert/delete test cases, never against a real sequence of deductions).

## 5. Gotchas / defects

- No behavioral bugs found — the extraction is faithful to the pre-existing logic bit-for-bit as far as the diff shows.
- Dead-code risk: `insert`/`delete`/`delete_candidate`/`delete_all_candidates`/`set_value` are unused in production code paths; a linter set to deny dead_code/unused pub items in a library crate might not catch this since they're `pub`, but a reviewer should flag that this is unexercised in integration.
- The struct still requires a full rebuild for the `execute()` trait method's fallback path (`let availability = StrategicGroupAvailability::from_grid(grid); self.execute_with_availability(grid, &availability)`), so strategies used outside the solver loop (any direct unit test or one-off call to `.execute()`) get zero benefit and pay the same construction cost as before — the sharing benefit only exists inside `Solver::execute_strategies_iter`.

## Answering the future-consumer API-tension questions

- **Fish strategies (Swordfish/Jellyfish)**: directly served today — the `rows`/`columns` fields are exactly what Swordfish's independently-reinvented private `GroupCandidateIndexes{rows,columns}` (on `add-swordfish-strategy`) duplicates. Swordfish is a textbook consumer of this exact abstraction and its authors evidently didn't know it existed (branches were parallel siblings off the same base commit).
- **"Exactly 2 positions in a group" (strong-link) queries**: cheap today, already used — XWing's `find_x_wings_axis` filters groups by `candidates.count() == 2` on the `CandidatesGroup` bitset, an O(1) popcount. So yes, this structure can answer "does this candidate have a strong link in this row/column/block" cheaply as-is; extending X-Cycles/Simple-Colouring/W-Wing (which each hand-rolled their own strong-link scan) onto it would be low-friction for row/column groups. For block-based strong links, the caller must additionally translate a `(block, row_major_block_index)` bit position back to a real `Position` — there's no `Axis::coordinates_to_pos`-style helper for blocks in the new module; callers must reach into the separate, older `position::BlockSegment::block_position`/`axis_position` API, which is a slight API-surface seam a future generalization (e.g. a chain-builder) would need to bridge.
- **Wings needing "sees" + bivalue**: not served. This structure is group-indexed by candidate, not position-indexed by candidate-count; "does cell X have exactly 2 candidates" (bivalue detection) and "do two positions see each other" are orthogonal queries this module doesn't attempt, and would need a separate, differently-shaped structure (e.g. per-position candidate-count index) — consistent with the branch survey's finding that 6 different branches independently hand-rolled "sees" helpers with no shared code.
- **Chains (strong links = exactly-2-position groups)**: as above, the per-group `count()==2` query is already cheap; what's missing for a chain-builder is (a) an iterator that yields, for a candidate, all groups (row/column/block) with exactly 2 positions along with the two resolved `Position`s (today's API gives bitsets, not resolved positions, and block resolution needs the external `BlockSegment` helper), and (b) since this branch's incremental-update path is unwired, a chain strategy built on top would inherit the same "rebuilt every step" cost rather than genuinely persistent state.

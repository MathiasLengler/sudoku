### 1. Correctness check vs Theory Spine

**Verdict: yes**, for the two rule types the task calls out, **but incomplete relative to the spine's own rule list**.

- Builds one graph per candidate value (`Value::all()` outer loop), edges = conjugate pairs (`find_all_strong_links`): scans rows, then columns, then blocks; any unit with exactly 2 candidate-holding positions becomes a bidirectional strong-link edge in a `BTreeMap<Position, BTreeSet<Position>>` adjacency map. A position can carry multiple edges (e.g. one row-conjugate + one column-conjugate partner), so this is a general graph, not a single linear chain.
- `build_chain_from_position` does a DFS/stack walk assigning alternating `Color::A`/`Color::B`, one connected component at a time (`build_color_chains` iterates uncolored candidate positions, skips already-colored ones). It does **not** detect odd-cycle conflicts up front — conflicts are discovered afterward by `has_color_conflict`, which is actually the correct behaviour: the spine's Rule 2 ("Twice in a Unit") is defined precisely as two same-colored cells sharing a unit, so deferring conflict detection to that check is consistent with theory rather than a bug.
- Rule 2 ("colour appears twice in a unit → colour false") ⇒ implemented as `try_type1_elimination` + `has_color_conflict`: correct match — checks all pairs within one color for shared row/column/block, eliminates that color's candidate everywhere, uses the opposite color's positions as the `Reason`.
- Rule 4 ("cell sees both colours → eliminate") ⇒ implemented as `try_type2_elimination` + `sees_any_of`: correct match — scans every off-chain candidate-holding position, checks if it shares a unit with at least one A-colored and one B-colored cell, eliminates there.
- **Gap**: spine also documents Rule 7 ("One Colour Empties a Unit" — a color that would strip all candidates from some unit if ON cannot be ON) — **not implemented**. Not asked about in the task's yes/no framing, but worth flagging since it's a documented rule this branch silently omits (spine is not marked UNKNOWN for this rule, unlike X-Cycles Part 2).
- `apply_elimination_rules` tries Type 1 before Type 2 and returns after the first hit per chain — so a chain that could yield both a Rule 2 and Rule 4 elimination in the same execute() call only reports one `Deduction`; not wrong (loop restarts and will pick it up again after the solver re-applies), but means single-chain output is not exhaustive per call.

### 2. Codebase-gap findings

- New data structures: `enum Color { A, B }` (2-valued, `opposite()` flip); chain representation `BTreeMap<Position<Base>, Color>`; strong-link adjacency `BTreeMap<Position<Base>, BTreeSet<Position<Base>>>` (rebuilt from scratch per candidate per `execute()` call, not persisted).
- Helper primitives (signatures only): `find_candidate_positions<Base>(grid, candidate) -> BTreeSet<Position<Base>>`; `find_all_strong_links<Base>(grid, candidate, &BTreeSet<Position<Base>>) -> BTreeMap<Position<Base>, BTreeSet<Position<Base>>>`; `build_chain_from_position<Base>(start, &links) -> BTreeMap<Position<Base>, Color>`; `build_color_chains<Base>(grid, candidate, &positions) -> Vec<BTreeMap<Position<Base>, Color>>`; `has_color_conflict<Base>(&[Position<Base>]) -> bool`; `sees_any_of<Base>(pos, &BTreeSet<Position<Base>>) -> Option<Position<Base>>` (the branch's own "sees" variant, distinct name from the other 6 identified in the survey).
- No reuse of any pre-existing group/candidate-availability infrastructure; row/column/block conjugate-pair scanning is done by hand with three near-identical copy-pasted loops (`find_all_strong_links`), not via `GroupCandidateAvailability`/`GroupCandidateIndexes`.

### 3. Pattern description for the owner

For a fixed candidate digit, collect every cell that still lists it, then find "conjugate pairs" — units (row, column, or block) where the digit currently has exactly two possible positions — and treat each such pair as a graph edge. Walk each connected component of this graph, alternating two colors, so that any two directly-linked cells always get opposite colors (this is exactly a bipartite 2-coloring, done via a plain DFS/stack, not a formal bipartite check). Two elimination rules then apply per component: if two cells sharing a unit ended up the same color, that color is provably false everywhere (Rule 2); otherwise, any off-chain cell that shares a unit with a cell of each color can have the digit removed (Rule 4). Requires only `Grid`, `Position`'s row/column/block accessors, and `Value`/`Candidates` — no other pre-existing solver infra. Gotchas: rebuilds the row/column/block conjugate scan from scratch per digit per call (no persistence across `execute()` invocations or across digits); returns at most one `Deduction` per chain per call even when multiple eliminations are possible; omits the spine's Rule 7; and has zero tests against a real sudokuwiki puzzle, so its correctness on a non-synthetic board is unverified by its own test suite.

### 1. Correctness check vs Theory Spine

**Verdict: partial / uncertain**, split by rule:

- Graph construction (`build_candidate_graph` → `add_links_for_rows/columns/blocks` → `add_links_for_unit`): per candidate, groups positions by row/column/block, and for any unit with ≥2 positions adds edges between **every pair** in that unit — `Strong` if the unit has exactly 2, `Weak` if ≥3. This matches the spine's strong/weak definitions directly ("if not A then B" for exactly-2, "if A then not B" for ≥3), and correctly treats weak links as all-pairs-within-a-unit rather than only adjacent pairs.
- Cycle search (`find_cycles_dfs`): DFS from every node, enforcing strict strong/weak alternation via `required_link_type = last_link.opposite()`, forbidding node revisits, capping path length at 12 (perf guard, not theory-driven), and checking for a closing edge back to `start` once `path.len() >= 4`.
- **Continuous loop (spine's Rule 1, fetched and confirmed)**: `process_cycle` treats a loop as continuous when `closing_link != last_link && closing_link != first_link`. Since `LinkType` is binary this reduces to "closing link is opposite of both its neighbors," which is a structurally plausible encoding of "alternates all the way round," and the elimination (`find_nice_loop_eliminations`) correctly walks every edge in the closed cycle (including the closing edge) and, for each **weak**-link edge, eliminates the candidate from any off-cycle candidate-holding cell that sees both endpoints — this matches the spine's Rule 1 quote ("eliminate on the units that can be seen by two or more cells that belong to the loop") for the fetched portion.
- **Discontinuous loop (spine's Rule 2, marked `UNKNOWN — Part 2 not fetched` in the spine)**: per instructions, flagging rather than judging. The code implements two special cases: both boundary links Weak with the second-to-last link Strong ⇒ eliminate the start node; both boundary links Strong with the second-to-last link Weak ⇒ set the start node's value. The extra constraint on `last_link` (as opposed to just checking `first_link == closing_link`) is not obviously required by general Nice-Loop theory as commonly described (the standard discontinuous-loop rule keys only on whether the two links touching the start node are both weak or both strong) — since internal alternation is already enforced by the DFS, `last_link` is a deterministic function of `first_link` and the path's edge-count parity, so this extra condition silently restricts which path lengths can trigger a discontinuous-loop deduction. This is a candidate defect, but cannot be checked against the spine (Part 2 unfetched) — flagged as **uncertain**, not scored as wrong.
- Path dedup (`visited_paths`) normalizes by **sorting** the node list before storing — this dedups by node *set*, not by actual cycle/edge sequence, so two genuinely different cycles over the same node set (different edge ordering) would incorrectly be treated as duplicates and only the first found reported. Concrete, checkable defect independent of the spine's Part 2 gap.

**Reference puzzles**: none. The spine's canonical X-Cycles example (Figure 4, chain `-8[A1]+8[A6]-8[C4]+8[H4]-8[H2]+8[J1]-8[A1]`, eliminations at B6/C5/H7) is **not** used anywhere in the test file. All tests are small synthetic 4×4 (`Base2`) grids in `mod tests { mod synthetic, mod link_detection }`, plus `strategy_snapshot_tests!(XCycles)`.

**Test quality vs dev template**: **partial**. Has (1) some pure-function tests (`test_sees_function`, `test_build_candidate_graph`) and (3) `strategy_snapshot_tests!(XCycles)` with a full new snapshot set — better template adherence than Simple Colouring. Still fails (2): no `assert_deductions_with_grid` against an actual sudokuwiki example board, so the strategy's real-world correctness (especially the continuous/discontinuous distinction, which only manifests on non-trivial boards) is unverified by its own tests.

### 2. Codebase-gap findings

- New data structures: `enum LinkType { Strong, Weak }` (`opposite()`); `type Node<Base> = Position<Base>`; `struct Edge<Base> { target: Node<Base>, link_type: LinkType }`; `struct CandidateGraph<Base> { adjacency: BTreeMap<Node<Base>, Vec<Edge<Base>>> }` (full adjacency-list graph, persists for one candidate's `execute()` sub-call only); `struct AlternatingPath<Base> { nodes: Vec<Node<Base>>, links: Vec<LinkType> }` (immutable-style path, `extend()` clones-and-appends rather than mutating in place — used recursively in DFS, so this is O(path_len²) cloning per branch explored).
- Helper primitives (signatures only): `build_candidate_graph<Base>(grid, candidate) -> CandidateGraph<Base>`; `add_links_for_unit<Base>(&mut CandidateGraph<Base>, &[Position<Base>])`; `find_cycles_dfs<Base>(grid, candidate, &graph, start, &path, &mut Vec<Deduction<Base>>, &mut BTreeSet<Vec<Position<Base>>>)`; `sees<Base>(pos1, pos2) -> bool` / `sees_both<Base>(pos, t1, t2) -> bool` (this branch's own "sees" variant, the 7th name for the same primitive per the survey); `process_cycle`, `find_nice_loop_eliminations`, `create_elimination_deduction`, `create_value_deduction`.
- Like Simple Colouring, rebuilds row/column/block grouping from scratch per candidate per `execute()` call; no reuse of `GroupCandidateAvailability`/`GroupCandidateIndexes`.

### 3. Pattern description for the owner

For a fixed digit, build a full graph over every cell still holding it: within each row, column, and block, connect every pair of candidate-holding cells, tagging the edge Strong if the unit currently has exactly two such cells or Weak if it has three or more. Then, from every node, depth-first-search for closed loops that strictly alternate Strong/Weak edges, capping search depth and pruning revisits, and classify each closed loop as continuous (fully alternating, including the closing edge) or discontinuous (the two edges touching the start node are the same type). For continuous loops, eliminate the digit from any off-loop cell that can see both endpoints of any weak edge in the loop; for discontinuous loops, either eliminate the digit at the start cell or place it there, depending on whether the matching boundary edges are both weak or both strong. Requires the same primitives as Simple Colouring (`Grid`, `Position` unit accessors, `Value`/`Candidates`) plus `Deduction::try_from_iters`/`Action::set_value`. Gotchas: cycle dedup is by node-set (sorted), not by actual edge sequence, so distinct cycles over the same cells may be silently dropped; the discontinuous-loop condition bakes in an extra `last_link` constraint whose theoretical justification is unclear and unverifiable against the spine (Part 2 page not fetched); `AlternatingPath::extend` clones the whole path per DFS branch; and the strategy is not part of `default_solver_strategies()`, so it never runs unless explicitly selected.

## Cross-branch: candidate link graph reconciliation

### What each existing (or peeked) implementation actually needs

| Branch | Link kinds needed | Scope | Structure shape | Traversal needed |
|---|---|---|---|---|
| Simple Colouring | Strong only | Per-candidate (one digit at a time, rebuilt fresh each digit) | Adjacency map, node = `Position`, multi-edge (a position can have a row-strong-link *and* a column-strong-link simultaneously) | Connected components + 2-coloring (bipartite walk) |
| X-Cycles | Strong **and** Weak (typed edges) | Per-candidate (one digit at a time, rebuilt fresh each digit) | Full adjacency list, node = `Position`, edges tagged with `LinkType` | Alternating-type cycle search (DFS with type-alternation constraint + start-node closure check) |
| W-Wing (peeked, read-only) | Strong only | Cross-candidate: computed **once per grid for all candidates simultaneously** (`Vec<Vec<StrongLink>>`, indexed by `candidate.get()-1`), then looked up per-candidate | Flat `Vec<StrongLink { pos1, pos2 }>` per candidate — no adjacency map at all, just an unordered pair list | None — direct pair enumeration + endpoint "sees" checks, no graph walk |

The three are not just "differently named" — they differ on a real axis: W-Wing only ever needs "list the strong-link pairs for digit X" (flat, no traversal); Simple Colouring needs "walk the strong-link graph and 2-color it" (adjacency, single link kind); X-Cycles needs "walk the strong+weak graph looking for alternating cycles" (adjacency, two link kinds, edge-typed traversal). All three currently rebuild their row/column/block conjugate-pair scan by hand and independently, duplicating exactly the per-unit candidate-position-count logic that `GroupCandidateAvailability`/`GroupCandidateIndexes` (see baseline doc, and `add-persistent-group-availability` branch) already formalizes elsewhere in the codebase — none of the three build on that structure even though "count of candidate positions per group" is precisely what a strong/weak link is derived from (count == 2 → strong, count ≥ 3 → weak).

### Proposed abstraction (shapes/signatures only, no impl)

A single persistent `CandidateLinkGraph<Base>`, built once per grid (ideally layered directly on top of a `GroupCandidateAvailability`-style per-candidate-per-group position index, converting each group's candidate-position set into edges instead of rescanning rows/columns/blocks by hand a third time):

- `struct CandidateLinkGraph<Base: SudokuBase> { adjacency: CandidateMap<Base, BTreeMap<Position<Base>, Vec<Link<Base>>>> }` — `CandidateMap<Base, T>` following the existing `StrategyMap`/`PositionMap` dense-array-by-key convention already used elsewhere in the codebase, keyed by candidate value instead of strategy/position.
- `struct Link<Base: SudokuBase> { to: Position<Base>, kind: LinkKind }`
- `enum LinkKind { Strong, Weak }`

Queries (shape only):
- `fn strong_links(&self, candidate: Value<Base>) -> impl Iterator<Item = (Position<Base>, Position<Base>)>` — flat unordered-pair view, directly serves W-Wing's use case (no graph walk needed) and is the same underlying data Simple Colouring's adjacency needs, just presented differently.
- `fn neighbors(&self, candidate: Value<Base>, pos: Position<Base>, kind: Option<LinkKind>) -> impl Iterator<Item = Position<Base>>` — adjacency-style access; `kind = Some(Strong)` gives Simple Colouring's graph; `kind = None` (or filtered post-hoc by the caller) gives X-Cycles' combined graph for its alternating DFS.
- Component/coloring and cycle-search algorithms stay **outside** this struct, as separate free functions/strategy-local code operating over `neighbors()` — the struct itself is a passive index (mirrors how `GroupCandidateAvailability` is a passive index consumed by XWing/GroupIntersection's own logic), not a place to bake in strategy-specific graph algorithms.

**v1 (minimal)**: node type = `Position<Base>`, single-candidate-scoped (build/query one digit's graph at a time, as all three current branches already do implicitly). This alone unifies Simple Colouring, X-Cycles, and W-Wing, and eliminates the row/column/block rescanning duplicated three times across the branches (plus the "sees" helper reimplemented 7 times per the survey, which this graph doesn't itself need to solve but which every consumer of it will still call for endpoint-visibility checks).

**v2 (later extension, not needed by the two branches in scope but relevant per the spine's Chaining family)**: generalize node type to `(Position<Base>, Value<Base>)` pairs. This is required once a strategy needs to mix candidates in one graph: the spine lists **3D Medusa** (multi-candidate extension of Simple Colouring — same coloring algorithm, but nodes now carry a digit) and **XY-Chains** (chains of bivalue cells where the "link" alternates between a same-cell bivalue relationship and a same-candidate strong link across different digits) directly under Chaining Strategies, both explicitly positioned as generalizations of what Simple Colouring/X-Cycles already do per-digit. A `(Position, Value)`-keyed graph subsumes the v1 `Position`-only graph as the special case where a per-candidate view fixes the second coordinate, so v1 can be treated as a scoped slice of v2 rather than a structure to be replaced later — worth deciding up front so the v1 type doesn't need a breaking rename when 3D Medusa/XY-Chains eventually land.

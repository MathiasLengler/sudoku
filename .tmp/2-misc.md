## 1. `origin/copilot/implement-new-bug-strategy` — BUG (Bivalue Universal Grave)

**Correctness vs Theory Spine: yes (with one unaudited edge case).**

- File: `sudoku-rs/src/solver/strategic/strategies/impls/bug.rs` (274 lines, whole diff is 293/-3 across 6 files — smallest strategy branch in the survey).
- Implements the spine's rule directly: scans `grid.all_candidates_positions()` (pre-existing helper, `grid/mod.rs:729` — not reinvented), requires every unsolved cell to have exactly 2 candidates except exactly one with 3 (any other count, or >1 trivalue cell, aborts with empty deductions); requires `bivalue_count > 0`. For the trivalue cell's three candidates, checks each of its row/column/block for a count of exactly 3 occurrences of that candidate, and places (`Action::SetValue`) the first candidate that satisfies it. Matches the spine's F8-`{3,4,6}` reasoning (a candidate appearing 3× in one of the trivalue cell's own groups is the one that must be placed, else two naked pairs would form).
- Doc comment explicitly states the uniqueness-assumption argument ("a full BUG state would lead to multiple solutions") — **flagged for later SAT-fit analysis** as instructed: this strategy has no meaning without the unique-solution assumption, unlike a pure elimination strategy.
- Unaudited nuance: if more than one of the trivalue cell's three candidates independently satisfied the "count == 3 in some group" test, the code silently returns the first match found (row, then column, then block) without checking for ambiguity. The spine's own reasoning implies exactly one candidate should ever satisfy this under a valid BUG state, so this is likely a non-issue in practice, but the code doesn't assert/guard it.
- **Test quality vs dev template: below the bar.** Only five plain `#[test]` unit tests against synthetic hand-built `Base2` grids (valid BUG+1, no-trivalue, multiple-trivalue, 4-candidate cell, empty grid). None of the three required template legs from the baseline are present except the first: no `execute()` test against a real sudokuwiki example board via `assert_deductions_with_grid` (the spine's own F8-`{3,4,6}` puzzle is never encoded), and **no `strategy_snapshot_tests!` macro invocation at all** — so this branch ships with zero insta snapshots, unlike every sibling strategy branch.
- Doc comment does cite `https://www.sudokuwiki.org/BUG` (matches spine URL), but only as a reference link, not as an actual test fixture.

**Codebase-gap findings:** none — `count_candidate_in_group<Base>(grid, group: impl Iterator<Item=Position<Base>>, candidate) -> usize` is a tiny one-off filter+count helper, not a new data structure; no duplication of existing infra. Wiring into `strategy_enum.rs` (`STRATEGY_COUNT` 9→10, new `StrategyEnum::Bug` variant + map field) and `sudoku-web/src/app/constants.ts` (`STRATEGY_NAMES`, `STRATEGY_OPTIONS.Bug` with correct link) is clean and complete, following the exact pattern of the other strategies.

**Pattern description for the owner:** Scan every unsolved cell; abort unless exactly one cell has 3 candidates and all others have exactly 2. For each of the trivalue cell's 3 candidates, count its occurrences among the cells of the trivalue cell's row, column, and block; if a candidate occurs exactly 3 times in one of those groups, place it in the trivalue cell (that's the only candidate a real, uniquely-solvable puzzle could resolve to — placing either of the other two would leave a duplicated naked pair elsewhere in that group, which is impossible with a unique solution). Requires only pre-existing grid/candidate accessors; no new primitives. Gotcha: relies on the uniqueness assumption exactly like Unique Rectangles/BUG do on sudokuwiki, so it has no SAT-solver equivalent path — it's a "the puzzle wouldn't be well-formed otherwise" argument, not a pure elimination. Test coverage is unusually thin for this codebase's conventions (no snapshot tests, no real-puzzle regression test) — worth adding both before relying on this code as-is.

## 2. `origin/copilot/add-chute-remote-pairs-strategy` — labeled Chute Remote Pairs, actually implements something else

**Correctness vs Theory Spine: no — wrong strategy entirely, self-admitted in its own UI text.**

- File: `sudoku-rs/src/solver/strategic/strategies/impls/chute_remote_pairs.rs` (410 lines; 17 files, +1429/-3, full snapshot set for base 2/3/4).
- The spine's Chute Remote Pairs is narrow and specific: **two** bivalue cells with an identical candidate pair, located in the same chute (one horizontal or vertical run of 3 boxes), that don't see each other; you then inspect the chute's third, unused mini-line/box for a candidate that appears there only once, and eliminate the other pair-candidate from cells both cells see.
- What this branch actually built is generic **Remote Pairs chains**: it collects *all* bivalue cells sharing a candidate pair anywhere on the grid (`find_bivalve_cells` — sic, typo for "bivalue"), groups them by pair, builds an adjacency graph over cells that "see" each other (`positions_see_each_other`), finds connected components of size ≥ 4, and 2-colors each component via BFS (`bipartite_coloring`) to test it's a valid alternating chain; any off-chain cell seeing one cell of each color gets both pair-candidates eliminated. There is **zero mention of "chute" anywhere in the algorithm, comments, or tests** (grepped: the word appears only in identifiers/struct names, never in logic). No chute-boundary check, no third-mini-line inspection — this is a completely different, more general strategy.
- The branch's own doc comment header calls it "Remote Pairs strategy" (not Chute Remote Pairs) and describes exactly the chain/bipartite-coloring technique. The web wiring makes the mismatch explicit: `sudoku-web/src/app/constants.ts` labels it `"Remote Pairs"` with `link: "https://www.sudokuwiki.org/Remote_Pairs"` — a *different* URL than the requested `/Chute_Remote_Pairs` page, and "Remote Pairs" is separately listed in the spine's family table under both "Chaining Strategies" and "Deprecated Strategies" (i.e. sudokuwiki itself treats plain Remote Pairs as supplanted, likely by 3D Medusa/X-Cycles). So this branch silently substituted a different, spine-classified-as-deprecated strategy under the requested name and even labeled it correctly as such in the UI — the mislabeling is really only in the branch/file/function names, not the author's own self-description.
- Test quality: three synthetic hand-built `Base3` unit tests (4-cell path chain, too-small component, odd-cycle/non-bipartite) plus `strategy_snapshot_tests!(ChuteRemotePairs)`. **No test cites or reproduces a sudokuwiki example puzzle at all** — not even the general Remote Pairs pattern — so there's no external validation this matches any published technique, generic or chute-specific.

**Codebase-gap findings:**
- `fn find_bivalve_cells<Base>(grid) -> Vec<(Position<Base>, Candidates<Base>)>` — ad hoc bivalue-cell scan, one of (per branch survey) at least 4 independent reimplementations across sibling branches (y_wing, xyz_wing, unique_rectangle-family, this one). Confirms the survey's finding #3; a shared "bivalue cell index" primitive is genuinely missing from `dev`.
- `fn positions_see_each_other<Base>(a, b) -> bool` — the 7th independent name for the "two positions share a unit" helper noted in the survey (joins `shares_house`/`sees_each_other`/`cells_see_each_other`/`sees`/`sees_both`/`shares_group`).
- `fn build_adjacency`, `fn bipartite_coloring`, `fn collect_component` — a small bespoke graph/BFS module (`Vec<Vec<usize>>` adjacency, `Vec<Option<u8>>` 2-coloring, `Vec<bool>` visited). **This machinery is not theory-required for the strategy that was actually requested** (Chute Remote Pairs needs no graph coloring — just a same-chute, same-pair, non-seeing cell pair plus a single mini-line candidate count). It *would* be the right shape of machinery for a genuine "Remote Pairs chain" strategy (which is exactly what got built), but that's a different, separately-named, spine-deprecated technique — so file it as over-engineering relative to the assigned task, appropriately-scoped relative to what it actually is.
- `fn group_by_candidates` — trivial `BTreeMap<Candidates<Base>, Vec<Position<Base>>>` bucketing, no reuse concern.
- Reuses pre-existing `Deductions::merge_deductions_by_reasons()` and `Reason::Candidates` correctly — no reinvention there.

**Pattern description for the owner (of what was actually built, i.e. generic Remote Pairs, for salvage if wanted under a correctly-scoped name):** Collect every bivalue cell, bucket by candidate pair, and build a graph connecting same-pair cells that share a row/column/block. For each connected component of at least 4 cells, check whether it's bipartite (BFS 2-coloring); a non-bipartite component (odd cycle) yields nothing. For a bipartite component, any other cell holding one or both pair-candidates that can see at least one cell from *each* color class must have both pair-candidates removed, because the two colors represent the two mutually-exclusive value assignments along the chain. Requires only bivalue-cell + pair-grouping + adjacency, all cheap to compute from existing grid accessors. Gotcha: this is not the requested Chute Remote Pairs strategy — it has no chute-boundary logic, doesn't require the two seed cells to avoid seeing each other in a chute-specific sense (general chain, not a single pair), and per the theory spine, "Remote Pairs" (unqualified) is listed among sudokuwiki's own deprecated strategies, so treat this as either (a) rename/rescope honestly as generic Remote Pairs if kept, or (b) discard and write the actual Chute Remote Pairs from scratch — the latter needs a bivalue-cell-index primitive but no graph/coloring machinery at all. No uniqueness-assumption reliance either way (pure elimination logic, safe for the later SAT-fit analysis to skip).

## 3. `origin/copilot/add-locked-sets-reasoning` — enriches existing LockedSets `Reason` payloads (not a new strategy)

**What it changes:** `LockedSets::execute` (`locked_sets.rs`) previously built a `Deduction` with populated `actions` (candidate deletions) but always-empty `reasons` — the file literally carried `// TODO: produce decuction reasons`, which this branch deletes. `v2::find_locked_set` is changed from returning a bare `CandidatesGroup<Base>` to a new `LockedSetResult<Base> { reduced_candidates_group, locked_set_info: Option<LockedSetInfo<Base>> }`, where `LockedSetInfo<Base> { locked_set_coordinates: Vec<Coordinate<Base>>, locked_candidates: Candidates<Base> }` carries which group-local coordinates form the found locked set and which candidates are locked to them. In `execute`, those coordinates are mapped back to grid `Position`s and, for each, `Reason::Candidates(locked_set_info.locked_candidates.intersection(grid[position].to_candidates()))` is inserted — intersecting with the cell's actual candidates because (correctly noted in a comment) not every cell in a naked triple necessarily holds every locked candidate (e.g. `{1,2}`,`{1,3}`,`{2,3}` locks `{1,2,3}` but no single cell holds all three).
- Handles the naked/hidden (transposed) duality correctly: for hidden sets the group-local "indexes" being searched represent candidate *values* rather than cell positions (an existing quirk of `v2`'s transpose trick), so the branch swaps which side becomes `locked_set_coordinates` vs `locked_candidates` depending on `is_transposed` — a bit confusingly named internally but consistent with the pre-existing code's own transpose convention, and spot-checked against one of the re-recorded snapshots (`base_3_sample_1_direct_candidates.snap`): the new reason payloads correctly point at the naked/hidden pair's own two cells with the locked pair's candidates, replacing what was previously an empty `reasons: []` / `"because of: "` string.
- Does **not** touch `deduction/reason.rs` at all — it only starts populating the pre-existing `Reason::Candidates` variant for this one strategy; it does not address the separate `Reason::Cell` TODO noted in the baseline (whole-cell/group UI highlighting is a distinct, still-open gap). No relation to the `Deduction`-level per-deduction-cost TODO either — untouched.
- Reuses the pre-existing `Deduction::try_from_iters` helper for the updated tests (already present on `dev`, not reinvented) alongside the older `try_from_actions`.

**Is it worth replicating by hand:** Yes, as a small, well-scoped improvement — it's exactly the TODO already on file in `dev`'s `locked_sets.rs`, the change is confined to two source files (135/-53 and 58/-20 lines respectively), the logic correctly accounts for the naked-vs-hidden asymmetry and the "not every cell holds every locked candidate" subtlety rather than naively dumping the full locked-candidate set into every reason, and the resulting reasons visibly improve UI explainability (turning blank "because of:" strings into concrete cell+candidate justifications). The main cost of adopting it as-is is API churn — `find_locked_set`'s return type changes from `CandidatesGroup<Base>` to a new struct, which is a breaking signature change for any other caller/benchmark harness (the file's own benchmark comment block references the old signature and would need updating) — but that's a mechanical follow-up, not a design problem.

**Snapshot churn breakdown:** Total diff is +4704/-782 across 21 files. Of that, the two actual source files account for 193/-73 = 266 changed lines; the remaining 19 files are all `.snap` snapshot fixtures (10 solver-level `solve_path`/`solve_path_all` snapshots + 9 per-strategy `locked_sets`/direct-candidates snapshots), totaling 4511/-709 = 5220 changed lines. **That's roughly 95% mechanical insta re-recording** (266 / 4704+782 ≈ 4.8% is hand-written logic), consistent with every prior deduction now carrying a non-empty `reasons:` block that insta captured verbatim — spot-checked one such diff and the re-recorded values are internally consistent (reason cells are the actual naked/hidden pair members, reason candidates are the actual locked pair), not garbage/placeholder churn.
